# i3 diagnostics

## Scope and access

Establish one symptom, when it started and the latest change. i3 runs on X11. AI Desktop reads without the user's graphical session, so `i3-msg`, `i3-dump-log`, `xrandr` and `xprop` usually cannot reach the X server or the IPC socket. A failed connection is missing visibility, not a fault; propose the read to the user. Read configuration files only within the allowed file scope.

## Identify the version and session

1. Running instance: ask the user for `i3 --moreversion` (or `i3 --version`) or `i3-msg -t get_version`. Offline: `i3 -v` prints the installed version and the date of the last commit.
2. Use the documentation of the installed version: `i3(1)`, `i3-msg(1)` and the i3 User's Guide.
3. Session start: `i3` with xinit from a TTY, or a display manager using the `i3.desktop` Xsession from i3-wm; `i3-with-shmlog.desktop` starts i3 with logging enabled. `~/.xsession` is where the man page configures locales and starts i3.

## Configuration and logs

- Search order: `~/.config/i3/config` (or `$XDG_CONFIG_HOME/i3/config`), `~/.i3/config`, `/etc/xdg/i3/config` (or `$XDG_CONFIG_DIRS/i3/config`), `/etc/i3/config`. The first found wins; `-c FILE` selects another file.
- On first start, `i3-config-wizard` creates `~/.config/i3/config` from the template `/etc/i3/config.keycodes`.
- `include PATTERN` (since 4.20): shell-like word expansion (tilde, variables, wildcards, command substitution); relative paths resolve against the directory of the file containing the `include`. Each file loads only once. An unreadable file is reported as an error and the rest of the config is still processed.
- `i3-msg -t get_config` returns the currently loaded config.
- IPC socket: by default `$XDG_RUNTIME_DIR/i3/ipc-socket.PID`; `I3SOCK` overrides it.
- Logs: release builds keep the SHM log disabled (`--shmlog-size` defaults to 0). Logging is enabled by starting i3 with `--shmlog-size=26214400` (e.g. via `i3-with-shmlog.desktop`) or at runtime with `i3-msg 'debuglog on; shmlog on; reload'`. `i3-dump-log` prints the log and needs a working X11 connection. If the user's `~/.xsession` redirects i3's output (the man page example uses `~/.local/share/i3/log`), read that file if allowed.

## Investigation

1. Syntax: `i3 -C` checks the config file and exits; add `-c FILE` to check a specific file. Run it only when the exact command is allowed. AI Desktop runs it only with `-c` and the file's path (e.g. `~/.config/i3/config`): the sandbox has no home directory, so it shows that file's directory read-only.
2. Outputs: ask for `i3-msg -t get_outputs` and `xrandr --current`; with RandR 1.5 or newer, `xrandr --listmonitors` lists the monitor objects i3 uses. Compare names with `workspace ... output` lines and `bar` settings. `tray_output primary` needs a primary output set with `xrandr --output NAME --primary`.
3. Binds: `bindsym` uses keysyms, `bindcode` physical keycodes; keycodes keep their meaning across layouts. Tools such as screenshot programs may need `bindsym --release`. Ask for `i3-msg -t get_binding_modes` when a mode seems stuck.
4. Window rules: ask the user to run `xprop` and click the window. In `WM_CLASS` the first value is the instance, the second the class. Compare with `for_window [class="..."]`; dialogs may need `window_role` or `window_type` criteria.
5. Autostart: `exec` runs only at initial startup, not on `restart`; `exec_always` also runs on restart. Without `--no-startup-id`, a program that does not support startup notification leaves the cursor busy for up to 60 seconds. ArchWiki suggests a dedicated XDG Autostart implementation as an alternative to `exec`.
6. Nagbar: buttons such as "Edit config" in `i3-nagbar` call `i3-sensible-terminal`; a non-working button can mean no recognized terminal emulator.

## Interpretation

- A passing `i3 -C` confirms syntax, not that a bind, output or rule works.
- `get_config` shows what the running i3 loaded; a difference from the file on disk may mean the edit has not been reloaded yet.
- An empty `i3-dump-log` on a release build can mean SHM logging was never enabled, not that nothing happened.

## Change and verification

Back up the file first. Propose the smallest diff and get consent for the write. Check it with `i3 -C -c FILE` when allowed. `reload` reloads the config; `restart` restarts i3 in place and re-runs `exec_always`. Each is a separate state change needing consent. Never `exit` i3 as part of diagnostics; it quits the window manager of the user's session. Verify with the same `i3-msg` read and the original symptom. Undo restores only your change.

## Result

Give the i3 version (installed and running), the config file actually loaded and its includes, the documentation used, the evidence, the validator result, and whether the change was proposed or applied and verified. Name the missing read when X11, IPC or the log was unavailable.
