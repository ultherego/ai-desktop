# Known limitations

AI Desktop is a development version, not a 1.0 release. Automated tests do not prove isolation; this list says what is still missing or has not been checked.

## Runtime and pending acceptance

The maintainer uses real Claude logins and requests on CachyOS, including long `max` reasoning turns with many commands. Still unchecked: a real Codex request under the client's system-call filter (and with it Codex's live answer), the Claude model list read from a real client with the offline `catalog` action (candidate 152), login expiry and renewal, and a fully fresh installation following README. The DMS widget shows Codex limits only; Claude limits are not read live from the service. Per-candidate evidence is in [ROADMAP.md](ROADMAP.md).

- The application package contains no vendor clients: it runs independently installed Claude Code or Codex.
- Supported system packages run directly. Official native/HOME/npm installations require explicit registration of the native payload and recognized resources; refresh approval is required after updating that source. Custom prefixes can use an explicit native path. Arbitrary shell/JavaScript wrappers, unsupported legacy JavaScript-only clients and unknown resource layouts are refused. Legacy Codex npm/standalone layouts without the current relocatable bundle contract are refused; update through the existing provider installer and register again, without requiring a pacman migration. Automatic discovery is not permission to execute. A root-owned executable or copied digest is not proof of vendor authenticity.
- Registrations are system-wide and take precedence over system packages. They retain approved bytes when the original installation changes; remove the registration explicitly to return to a system package. Neither registration nor the application updater upgrades the original provider installation.
- Required offline compatibility probes gate execution. A newer version that passes within the supported version family remains explicitly untested. The probe checks adapter prerequisites, not every behavior or future reply; actual protocol validation still runs during use.
- Bound client/private-resource snapshots prevent an unchecked replacement from becoming the payload of an ongoing operation. Each sequential child receives linked canonical files on private tmpfs, remounted read-only before execution; snapshot descriptors do not reach the native client. Memory can include 768 MiB of retained sealed snapshots plus 768 MiB of child tmpfs files, sharing the 3 GiB analysis/quota ceiling with native-client memory. Both native clients passed offline checks through this materialization path on CachyOS; kernel mutation and descriptor checks also passed in both CI Bubblewrap jobs. Source changes refuse following phases. The root-managed OS libraries under the existing read-only `/usr` environment are not snapshotted; finish operations before system upgrades.
- One approval covers a bounded project analysis or a standalone task with an explicitly declared test. Ordinary `ask` and project-edit copy tests still ask before execution; unifying their preparation/data-transfer/test scope and durable task continuation remains open. Final writes always require the exact diff approval.
- Interactive `ask` saves local checkpoints by default (`--no-save` keeps a temporary conversation) and `ai-desktop -c` resumes the newest one with its whole read-back thread. A checkpoint failure is reported and leaves the conversation in memory, but the automatic first-save attempt is not retried in the same process. The model receives only the newest exchanges that fit the request window and the bounded task memory: there is no semantic compaction of older turns. Claude and Codex answers in a conversation appear block by block while they are written (Codex's live text is checked with synthetic tests only until a real Codex request is run again under its system-call filter). A web search shows its progress, but its answer appears only after the sources are checked; `material`/`project`/`task` answers also appear only at the end. Each turn still starts its own client process in a fresh sandbox (the maintainer's decision of 2026-11-09).
- An open conversation keeps its privileged session for up to 15 minutes without a question (4 hours in all). An idle session is closed when the next question finds it expired or the conversation ends, not by a timer, so its helper unit may stay registered while the window sits idle; its own 4-hour limit and `ai-desktop stop` still end it. After the session is reopened, `sudo` may ask for the password again. A service restart during a request (for example its 4-hour unit limit, counted from the first terminal that started it) ends that request; the next one connects anew. At most 16 conversations per user can hold a session at once. `ai-desktop stop` in another terminal ends a question that is being answered in a conversation (the conversation continues and the next question opens a new session). If a helper ends without confirming its cleanup, for any reason, the conversation continues with a new session; when the conversation ends it warns to check `ai-desktop stop` and exits with code 2.
- A saved conversation keeps what you typed or pasted, including any secret, until you delete it with `ai-desktop sessions`; there is no automatic retention period. Saving is chosen per run with `--no-save`, not by a persistent setting.
- The read-back thread of a saved conversation holds up to 2000 turns and 256 KiB per question or answer; beyond that, or when the record reaches 16 MiB, the oldest turns are no longer shown. Only the newest turns that fit the request limits are sent to the model, so the model does not remember the whole thread. Provider token limits can be lower than the application's byte ceilings.

- When a question searches first and then works locally, what the search found reaches the local planning as data: a page could try to steer the model. It still can only use your allowed commands and reads, and any write needs its exact diff approved; review a diff after a web search as carefully as any other. The search runs at most once per question and only before anything local was collected.
- An address inside a code example of a web answer is shown as part of the code, unchecked; only addresses in the list of sources are proven to come from the search.
- A web answer that fails the checks of its transcript or text may be asked once more, silently, while at least half of its time is left: the search provider then receives the same question and conversation a second time.
- A conversation's session helper is kept for 4 hours plus the longest answer; a question sent at the very end of that time that first waits long for a free place can outlive it and is then cut off (ask again). A `task run` approval does not yet excuse a wait for a free place the way a conversation question does.
- A web search receives the latest exchanges of the conversation, so details an earlier answer quoted (a log line, a path) reach that request too. Claude is told to keep personal details out of search queries; nothing enforces it.

- A `host_sockets` entry is bound only if it is a socket when the command starts; a process able to write in that part of `/run` could still swap the path between that check and Bubblewrap's bind.

## Conversation look
- The full-screen view keeps its own copy of what it showed (up to 20000 rows) to page back through it. Characters that take two cells (some CJK and emoji) count as one there, so an earlier row containing them may be drawn a little shifted; what `sudo` prints when it asks for the password is not in that copy. Copying a selection relies on the terminal accepting OSC 52 (most do, also through Zellij and tmux when allowed) or on `wl-copy` on Wayland; without either, hold Shift and use the terminal's own selection. A selection covers the conversation area only, not the input. A terminal without SGR mouse reports (very old terminals) may type the wheel's bytes as text; use `--inline` there.
- The input pinned to the bottom grows to about half the window; longer text scrolls inside it with the cursor. Characters that take two cells (some CJK and emoji) are counted as one when wrapping, so such a row can be cut a little late.
- In the `--inline` view the pinned input relies on the terminal's scroll region. After a resize the conversation is drawn again from the saved thread: questions and answers, without the command rows of earlier turns; each redraw also leaves a copy in the terminal's scrollback. Text written by other programs into the same terminal can land in the band until the next redraw.

- During a turn, a `/` menu opens at once and its choice is applied after the answer. Output the model's turn prints while the menu is open lands in the same place and can disturb the menu until it is redrawn; `/provider`, `/test` and `/exit` still wait for the answer. A program started during a turn that reads the terminal without taking the lease (today only `sudo -v` reads it, and it takes the lease) would compete with the live input for keys.

## Security
- The sandbox for read commands shows an empty `/run` apart from a fixed list, so Docker, systemd varlink and other daemon sockets are hidden unless listed in `[commands] host_sockets`. The system D-Bus is reached only through a filter (`xdg-dbus-proxy`) that passes a fixed list of read methods (property reads, introspection, listing units, sessions, links, devices, snapshots); everything else, including DNS lookups and state changes, is refused. A read tool that needs a method outside the list fails until the list is extended, and `resolvectl status` needs the resolver socket in `host_sockets`, which also allows DNS lookups. Without `xdg-dbus-proxy` commands get no D-Bus. An opted-in socket gives whatever its daemon allows; Docker's is root-equivalent. Put only strictly read-only commands in `allow`.
- A template ending in `...` passes any further plain words to a read command; the sandbox (read-only files, no network, filtered D-Bus, hidden sockets) is what limits it, and paths among the words are checked against `files`. `commands.deny` blocks whole commands by their leading words, but not every spelling of a flag (`-a`, `--all`, `-qa`). A change template ending in `...` runs whatever arguments the model chose after your `yes`, so read the full command before confirming.
- A file's content or a command's output can lead the model to further allowed reads, and their results go to the provider. The boundary is `permissions.toml` and the per-question budgets.
- The Claude Code client has access to its own login profile in the separate `ai-desktop` account. The client's system-call filter is a deny list of kernel interfaces it never needs, not an allow list: an ordinary call that is not listed stays allowed.
- Application packaging no longer authenticates provider downloads with its own pinned checksums. Install clients from a source you trust, and review registration payloads before approving them. Metadata, stable operation binding, capability checks and vendor provenance are separate properties; none substitutes for the others.
- There is no protection against a hostile process of the same user and no guarantee on power loss.
- The model does not see a BOM or Windows line endings, so it will not answer whether a file has them. A file with mixed line endings can be read but not edited, because the write would not reproduce its bytes. A file with a bare CR in the middle of the text is refused on read as well. The model works with normalized text. The isolated test copy restores the original supported line-ending and BOM format.

## Behavior
- Writing an existing file replaces it atomically and refuses the write if an editor changed the file after the last check. A write through a file the editor already held open can still land in the old version right after the comparison, before that version is removed. This requires a file system with `RENAME_EXCHANGE` (Btrfs, ext4, xfs, tmpfs); on others the write is refused.
- If consent expires or permissions change during a `[commands] change` command, the program does not run the test or the undo: it shows them for you to run by hand. Such a turn ends in a refusal, so the result stays on screen but may not reach the conversation memory.
- A truncated task journal blocks writing in that directory until it is checked by hand. History and the task trash have no automatic cleanup, and the limit is 128 entries of each per directory. `task prune` removes only finished entries the owner chooses; a deletion must be restored first, because pruning never deletes user files.
- A file name in `deny` must be written exactly as it is on disk: the rules do not normalize Unicode characters.
- A text `find` in `ai-desktop` reads up to 64 MiB of file contents per search and skips files over `file_size`, binary or non-UTF-8 files and (policy version 1) private keys; any skipped file marks the result incomplete. It matches case-insensitively by literal text, not by regular expression. An edit of a file above `read_file_size` needs excerpts read earlier in the same question (in `ai-desktop project`, lines Claude already received of the same file version); without them `ai-desktop` sends one correction and `project` refuses with the setting named.
- Edited files are limited to 8 MiB each and 16 MiB combined, with up to 64 changes. Full model output is smaller; use anchored replacements for large files. Configured lower read budgets remain effective. Local copy defaults are independent: 2,000 files, 8 MiB each and 64 MiB combined (hard ceilings 20,000 / 32 MiB / 128 MiB). A project test requires the entire supported authorized index to fit its copy limits. Go and npm refuse when the user manager cannot enforce the required cgroup limits. Local runtime dependencies must already be available.
- Project test copies currently support bounded UTF-8 text and restricted relative path names. Binary assets and unsupported names (including npm `@scope` directories) cause an explicit refusal; they are not silently omitted to obtain a passing test. Dependency installation and arbitrary build commands are not available. The project is rechecked before tests, after tests and before applying edits, but the whole source tree is not atomically frozen against concurrent writers.
- In `ai-desktop project` the change preview warns when the project has test files and a code change is checked only for syntax; this recognises test files by their names (`test_*.py`, `*_test.py`, `*_test.go`, `*.test.js|ts`, `*.spec.js|ts`) and cannot see whether those tests cover the change. The model is instructed to declare the suite, but the choice remains the model's and the warning does not block the save.
- In `ai-desktop project` one approval covers follow-up questions of the same task (S9). It ends when a file in the index changes, so a change you just saved through AI Desktop makes the next question ask again; there is no exception for the program's own writes. A provider failure inside a question keeps the task; a refusal or Ctrl+C ends it. In `ai-desktop` (ask), a test on a copy still asks once per proposal, because conversation consent never covers running code.
- Commands run in a sandbox without network or user session, so for example `ip`, `wpctl` and `glxinfo` do not see the host's state.

- The agent panel shows the last quota windows actually reported by each client, including their observation time. With no observations or after a reset the current balance is unknown. The widget timer refreshes local data. On-demand Codex limits require a separate, explicitly linked native Codex session for the chosen workspace. The signed-in browser account used for ChatGPT app usage may differ.
- Local mode trusts the service on the configured loopback port. Selecting this service does not install, launch or authenticate the server process.
- New configurations expose the general Skills catalog. Explicit setup fills empty predefined roles; existing saved assignments remain authoritative. All four conversation modes load procedures and reference sections on demand. Whole-material map/reduce requires the relevant knowledge to be loaded before the plan starts; a late knowledge request refuses the plan instead of skipping a material part.

## Not checked
- Login expiry and refresh, and real network failures with the official client.
- An independent security review and installation on a fresh system.
- Anthropic's terms for a program that runs Claude Code with a subscription login; you use the client on your own account and at your own judgment.

- Packaged documentation is a dated snapshot. A rolling wiki page is not proof that every option exists in the installed tool; unknown or incompatible applicability must remain explicit. Live official-document retrieval and automatic environment-pack reconciliation are follow-up work. Loaded-resource reuse is limited to the running conversation; it is not restored from a saved session.
